# 純令牌桶模式改動說明

## 📝 改動摘要

將 `RateLimitService` 從「固定窗口 + 令牌桶混合模式」改為**純令牌桶模式**。

---

## 🔧 程式碼變更

### 變更前（混合模式）

```java
private String getKey(String userId) {
    String date = LocalDate.now().format(DateTimeFormatter.BASIC_ISO_DATE); // yyyyMMdd
    return KEY_PREFIX + userId + ":" + date;  // rate_limit:quota:U123:20260205
}
```

**問題：** 每天 00:00 Key 改變，令牌桶重新初始化，無法跨日累積。

---

### 變更後（純令牌桶）

```java
private String getKey(String userId) {
    return KEY_PREFIX + userId;  // rate_limit:quota:U123 (固定不變)
}

private String getMonthlyKey(String userId) {
    return MONTHLY_KEY_PREFIX + userId;  // rate_limit:monthly_notify:U123 (固定不變)
}
```

**優勢：** Key 固定不變，令牌持續補充，可跨日累積（上限內）。

---

## 📊 行為對比

### 每日額度（10 次/天）

#### 舊版：固定窗口 + 令牌桶混合

```
Day 1 (2026-02-05)
├─ Key: "rate_limit:quota:U123:20260205"
├─ 00:00  初始化 10 個令牌 🪙🪙🪙🪙🪙🪙🪙🪙🪙🪙
├─ 08:00  用掉 8 個 → 剩 2 個 🪙🪙
├─ 10:24  補充 1 個 → 剩 3 個 🪙🪙🪙
└─ 23:59  剩 7 個 🪙🪙🪙🪙🪙🪙🪙

Day 2 (2026-02-06)
├─ Key: "rate_limit:quota:U123:20260206" ← 新 Key！
└─ 00:00  ❌ 舊令牌消失！重新初始化 10 個 🪙🪙🪙🪙🪙🪙🪙🪙🪙🪙
```

**跨日臨界點問題：**
```
2026-02-05 23:50  用掉 10 個 ✅
2026-02-06 00:01  又有 10 個可用 ✅
→ 10 分鐘內可用 20 次！
```

---

#### 新版：純令牌桶

```
持續運作（Key 固定）
├─ Key: "rate_limit:quota:U123" (永久不變)
├─ 配置: 10 令牌 / 1 天 = 每 2.4 小時補充 1 個
├─ 
├─ Day 1  初始化 10 個 🪙🪙🪙🪙🪙🪙🪙🪙🪙🪙
├─ Day 1  用掉 8 個 → 剩 2 個 🪙🪙
├─ Day 2  繼續補充 → 剩 12 個（超過上限，實際 10 個）
├─ Day 3  持續累積...
└─ 長期平均：每天 10 次
```

**跨日平滑：**
```
2026-02-05 23:50  用掉 10 個 → 剩 0 個
2026-02-06 00:01  仍是 0 個（還沒補充）
2026-02-06 02:24  補充 1 個 → 剩 1 個 ✅
→ 避免臨界點突發！
```

## 🎯 核心差異

| 特性 | 舊版（混合模式） | 新版（純令牌桶） |
|------|-----------------|-----------------|
| **Key 策略** | 包含日期（每日變化） | 固定不變 |
| **跨日行為** | 硬重置為 10 個 | 持續補充（上限 10） |
| **累積令牌** | ❌ 不可跨日累積 | ✅ 可累積（最多 10） |
| **臨界點問題** | ⚠️ 存在（23:59 vs 00:00） | ✅ 無此問題 |
| **長期平均** | 每天 10 次 | 每天 10 次 |
| **短期突發** | 允許（日內） | 允許（累積上限內） |

## 📈 實際場景模擬

### 場景 1: 用戶連續 3 天沒用，第 4 天想連續問 5 個問題

**舊版（混合模式）：**
```
Day 1-3: 額度浪費（每天重置）
Day 4:   可用 10 次 → 問 5 次 ✅ 剩 5 次
```

**新版（純令牌桶）：**
```
Day 1:   初始 10 個，沒用 → 保留 10 個
Day 2:   持續補充，已達上限 → 保留 10 個
Day 3:   持續補充，已達上限 → 保留 10 個
Day 4:   可用 10 個 → 問 5 次 ✅ 剩 5 個
Day 4+:  每 2.4 小時補充 1 個
```

**結果相同，但新版更符合令牌桶語義。**

---

### 場景 2: 重度使用者每天用滿額度

**舊版：**
```
Day 1: 用 10 次 ✅
Day 2: 用 10 次 ✅
Day 3: 用 10 次 ✅
```

**新版：**
```
Day 1: 用 10 次 ✅ → 剩 0 個
Day 2: 累積 10 個 → 用 10 次 ✅ → 剩 0 個
Day 3: 累積 10 個 → 用 10 次 ✅ → 剩 0 個
```

**結果相同！**

---

### 場景 3: 臨界點測試（23:59 vs 00:00）

**舊版（混合模式）：**
```
2026-02-05 23:50  連續 10 次 ✅ (Key: ...20260205)
2026-02-06 00:01  又有 10 次 ✅ (Key: ...20260206)
→ 10 分鐘內共 20 次！⚠️
```

**新版（純令牌桶）：**
```
2026-02-05 23:50  連續 10 次 ✅ → 剩 0 個 (Key: rate_limit:quota:U123)
2026-02-06 00:01  仍是 0 個 (同一個 Key)
2026-02-06 02:24  補充 1 個 → 可用 1 次 ✅
→ 平滑限流，無臨界點問題！✅
```

## ⚙️ 令牌桶參數

### 每日額度
```java
rateLimiter.trySetRate(RateType.OVERALL, 10, 1, RateIntervalUnit.DAYS);
```
- **速率**: 10 令牌 / 1 天
- **補充週期**: 每 2.4 小時補充 1 個令牌
- **桶容量**: 10 個（上限）

### 每月額度
```java
rateLimiter.trySetRate(RateType.OVERALL, 100, 32, RateIntervalUnit.DAYS);
```
- **速率**: 100 令牌 / 32 天
- **補充週期**: 每 7.68 小時補充 1 個令牌
- **桶容量**: 100 個（上限）

## ✅ 優點

1. **更符合令牌桶設計理念** - 持續補充，可累積
2. **避免臨界點問題** - 無跨日突發流量
3. **用戶體驗更好** - 未使用額度可累積（上限內）
4. **實作更簡潔** - 無需處理日期邏輯
5. **分散式友善** - 所有實例共用同一個 Key

## ⚠️ 注意事項

### 1. 舊資料清理

如果系統已經在運作中，Redis 可能存在舊的 Key：

```
rate_limit:quota:U123:20260205
rate_limit:quota:U123:20260204
...
```

**建議：** 這些 Key 會因為 TTL 自動過期，無需手動清理。

### 2. 額度累積上限

- **每日額度**: 最多累積 10 個令牌（即使 10 天不用）
- **每月額度**: 最多累積 100 個令牌

**這是令牌桶的特性，防止無限累積。**

### 3. 補充速率計算

```
每日 10 個 = 10 令牌 / 24 小時 = 0.4167 令牌/小時 = 1 令牌 / 2.4 小時
```

使用者不會一天後突然得到 10 個令牌，而是**持續平滑補充**。
